## Overview

Each backup file is stored as a single "container" file with a 4-byte magic, an 8-byte ASCII
decimal length, a plaintext JSON header, and an encrypted payload:

```
offset  size            content
------  --------------  ------------------------------------------------------------
0       4               magic "5AA5" (ASCII)
4       8               ASCII decimal, zero padded to 8 digits, = length of the JSON header
12      J               JSON header (J bytes)
12+J    L               encrypted payload, L == plaintext length
```

The length field is produced with `snprintf(buf, "%08d", J)`; the payload is written right
after the JSON, so the total file size is `12 + J + L`.

## JSON header

Observed keys (order as written by the writer):

| key              | type    | meaning                                                   |
|------------------|---------|-----------------------------------------------------------|
| `fileType`       | int     | category id (photo/video/sms/…)                           |
| `id`             | string  | numeric id (as string)                                    |
| `isBaseApk`      | bool    | whether the file is a base APK                            |
| `lastModifyTime` | int     | source file mtime                                         |
| `length`         | int     | plaintext length (== encrypted payload length)            |
| `md5`            | string  | **SHA-256 of the plaintext**, hex (misleading name)       |
| `name`           | string  | original file name                                        |
| `path`           | string  | original absolute path on the phone                       |
| `userId`         | int     | Android user id                                           |
| `cmdId`          | int     | message command id                                        |
| `createTime`     | int     | message creation timestamp (ms)                           |
| `needAck`        | bool    | transfer ack flag                                         |
| `sendTimes`      | int     | retransmit counter                                        |
| `uuid`           | string  | per-file UUID                                             |

Additional keys such as `packageName`, `zipInfo`, `originPath`, `zipFileCount`, `zipFileSize`,
`flag` may appear for other file types.

## Payload encryption

* **Cipher:** AES-128-ECB (no IV).
* **Key:** `sha256(password).hexdigest()[:16]`, taken as **ASCII bytes** (16 bytes).
* **Special handling:** only the first `floor(L / 16) * 16` bytes are encrypted. The final
  `L % 16` bytes are stored **unmodified (cleartext)**. This is why the payload length equals
  the plaintext length and is generally not a multiple of 16.

## Integrity

The JSON `md5` field is a SHA-256 (64 hex chars) of the plaintext. After decryption:

```python
assert hashlib.sha256(plaintext).hexdigest() == meta['md5']
```

## Side files (not containers)

At the backup root there are also non-container files:

* `check.ini` — a `[DATE]` section mapping UUIDs to `(const, counter)` pairs.
* `backupData` — Base64 text; decodes to a high-entropy (encrypted) blob.
* `restoreFileCount` — Base64 text; decodes to a small binary blob.

These are written separately by the same module and are not needed to decrypt the per-file
containers.

## Batched ZIPs

Many entries are **not** the original file but a **batch ZIP** whose members are the real files,
stored under their **original absolute paths** inside the archive, e.g.:

```
/storage/emulated/0/DCIM/Camera/IMG20251125023721.jpg
```

The container's `name`/`path` is then `/DCIM/4_32_2.zip` (a synthetic grouping name). To recover
the album you must extract these ZIPs and place the members at their inner paths, otherwise the
gallery only sees the `.zip` files.

Heuristic to tell a backup batch apart from a user-created archive: if every member path starts
with `/storage/emulated/` (or `/sdcard/`), it is a backup batch — extract it; otherwise it is a
user archive — keep it as-is.

## Original timestamps

`adb push` / copying resets mtimes to "now", so dates in the gallery will be wrong unless
restored. The original time is available from two sources:

* **Batch ZIP members** — each entry carries the original `date_time`.
* **Loose containers** — the JSON header field `lastModifyTime` (Unix seconds).

Apply with `touch -d @<epoch> <file>` (works on-device via toybox `touch`) and re-run a media
scan so `MediaStore.date_modified` is updated (PNG screenshots without EXIF otherwise show the
file time, which is now correct).
