These notes describe how the container format and key derivation were derived from the
desktop assistant (`coloros-assist`, an Electron app) that produced the backup.

## Components

The desktop assistant ships a small set of native modules:

| file                 | role                                                        |
|----------------------|-------------------------------------------------------------|
| `SocketConnect.dll`  | socket protocol + `DataCenterManager` + file transfer       |
| `Utils.dll`          | crypto wrappers (`AesImpl`, `HashImpl`, `RsaImpl`, …)       |
| `NodeImpl.node`      | Node addon bridging JS ↔ native                              |
| `Adb.dll`, `Track.dll` | device control / telemetry                                |

`SocketConnect.dll` imports from `Utils.dll`:
`AesImpl::{aesEncrypt, aesDecrypt, aesEncryptPadding, aesDecryptPadding, aesGenKey}` and
`HashImpl::{GetHash, addData, resultToHex, …}`.

## Locating the container writer

Searching `SocketConnect.dll` for the ASCII literal `5AA5` yields the format string followed by
`%08d` and the JSON keys (`uuid`, `cmdId`, `fileType`, `length`, `md5`, `name`, `path`, …).
The writer is `DataCenterManager`'s file-transfer class:

* `FileTransfer::Encode` — builds `"5AA5"` + `snprintf("%08d", len)` + JSON, then encrypts the
  data and appends it.
* `FileTransfer::Decode` — the inverse (used on restore).

## Cipher resolution

`AesImpl::aesEncrypt(std::string &out, std::string const &in, AesMode mode, std::string const &iv)`

* `AesMode` is an index into a static map built at load time. Index `0` maps to a static
  OpenSSL `EVP_CIPHER` descriptor.
* Reading the descriptor at its `.rdata` address gives the fields
  `nid=0x1A2 (418)`, `block_size=16`, `key_len=16`, `iv_len=0`.
* `nid 418` is `NID_aes_128_ecb`; `iv_len = 0` confirms **ECB** (no IV).

`FileTransfer::Encode` calls `aesEncrypt(buf, this->key, /*mode*/ 0, /*iv*/ "")` — the third
argument is the mode (`0` = ECB) and the fourth is an empty IV. The key is a `std::string`
member of the `FileTransfer` object.

## Key derivation

* `DataCenterManager::SetBackupPasswordAndTip(name, password, tip)` stores the password (and
  phone name / tip) into the `BackupFileInfo` object. The key string is truncated or
  zero-padded to 16 bytes (`FUN_180030560`).
* In the Electron JS side, `setBackupPassword(pw)` hashes the password before handing it to
  the native layer:
  ```js
  setBackupPassword(pw) { const l = hash(pw, "sha256"); De.SetBackupPasswordAndTip(name, l, tip); }
  ```
* `hash(pw, "sha256")` returns the **hex string** of the SHA-256 digest. The native code then
  takes the first 16 characters of that hex string as the 16-byte AES key.
* Net result: `key = sha256(password).hexdigest()[:16].encode('ascii')`.

## Why the tail stays plaintext

The encryption path uses the OpenSSL EVP API: `EVP_EncryptUpdate(...)` is called, but
`EVP_EncryptFinal(...)` is **not** invoked (or its output is discarded). Therefore only complete
16-byte blocks are transformed; the trailing `len % 16` bytes are copied through untouched and
written in cleartext. This produces the observed "length preserving" behaviour.

## Verification

Decrypt the first block(s) of any container with the derived key and compare against the
header `md5` (the plaintext SHA-256). All 437 container files in the test set verified
successfully; the only two mismatches were partial fragments of very large videos that are
stored whole in another backup run.

## Security implications

The scheme has **no salt, no KDF iterations and no device binding**:

* The key is a pure function of the password ⇒ identical plaintext gives identical ciphertext
  across backups.
* The key space equals the password space. A 6-digit numeric password can be brute-forced in
  seconds (each attempt only needs to ECB-decrypt a single 16-byte block and check for a
  plausible result).
* AES-ECB additionally leaks equality/structure between 16-byte blocks.

Treat the backups as effectively unencrypted.
